## 1. 视觉模型的国内可选方案 & 本地部署选择

### 1.1 当前实现方式

视觉模型在代码中位于 `app/lg_agent/lg_builder.py` 的 `create_image_query` 函数中，通过 **aiohttp 直接 HTTP POST** 调用 OpenAI 兼容接口（`/chat/completions`），不经过 `LLMFactory` 路由体系。

```python
# 当前硬编码的三个配置项
VISION_API_KEY=sk-xxxx
VISION_BASE_URL=https://ai.devtool.tech/proxy/v1
VISION_MODEL=gpt-4o
```

调用流程：图片 → PIL 压缩（最大 1024px）→ JPEG base64 → HTTP POST 到视觉模型 → 获取图片描述 → 将描述交给 AGENT_SERVICE 做最终回复。

### 1.2 国内云 API 可选方案

只要是兼容 OpenAI `/chat/completions` 格式的 API 都能直接替换，无需改代码。

| 服务商 | 模型 | `VISION_BASE_URL` | 备注 |
|--------|------|-------------------|------|
| **DeepSeek** | `deepseek-chat` | `https://api.deepseek.com` | 与现有 DEEPSEEK_API_KEY 共用 |
| **阿里通义千问** | `qwen-vl-max` / `qwen-vl-plus` | `https://dashscope.aliyuncs.com/compatible-mode/v1` | 中文识别优秀 |
| **智谱 GLM** | `glm-4v` | `https://open.bigmodel.cn/api/paas/v4` | 多模态能力强 |
| **阶跃星辰** | `step-1v-8k` | 需查官网 | 长上下文视觉理解 |
| **硅基流动** | 多种视觉模型 | `https://api.siliconflow.cn/v1` | 聚合平台，选择多 |

**推荐优先级**：
1. **DeepSeek** — 已有 key，零额外成本，即配即用
2. **硅基流动** — 聚合多个模型，切换方便，按量付费

### 1.3 本地部署方案（RTX 5060Ti 8GB 显存）

5060Ti 8GB 显存可以流畅运行 7B-8B 级别的视觉模型。

#### 方案 A：Ollama 部署（推荐，最简单）

```bash
# 推荐：MiniCPM-V 8B（端侧专用，显存占用约 6GB）
ollama pull minicpm-v:8b

# 备选：LLaVA 7B（经典视觉模型，显存占用约 5GB）
ollama pull llava:7b

# 备选：LLaVA 13B（需确认显存是否足够）
ollama pull llava:13b
```

> **注意**：Ollama 的视觉 API 格式与 OpenAI 略有不同（图片传参方式），当前代码直接 HTTP POST OpenAI 格式，本地部署 Ollama 视觉模型时需要调整 `create_image_query` 函数中的请求体格式。

#### 方案 B：vLLM / LMDeploy 部署（性能更好）

```bash
# 安装 vLLM
pip install vllm

# 部署 Qwen2.5-VL-7B-Instruct（需显存约 8GB，量化后更小）
vllm serve Qwen/Qwen2.5-VL-7B-Instruct --port 8000
```

vLLM 原生支持 OpenAI 兼容接口，与现有代码兼容。

#### 本地模型选型对照

| 模型 | 大小 | 显存占用 | 中文能力 | 推荐场景 |
|------|------|---------|---------|---------|
| **MiniCPM-V-2.6** | 8B | ~6GB | ⭐⭐⭐⭐⭐ | 中文图片理解首选 |
| **Qwen2.5-VL-7B** | 7B | ~7GB | ⭐⭐⭐⭐⭐ | 通义千问视觉，中英文俱佳 |
| **LLaVA-1.6** | 7B | ~5GB | ⭐⭐⭐ | 英文为主，中文一般 |
| **InternVL2-4B** | 4B | ~4GB | ⭐⭐⭐⭐ | 模型小但能力强 |

## 2. 为什么没有 VISION_SERVICE？

### 2.1 现状分析

当前的服务路由体系：

```
LLMFactory（工厂模式）
├── create_chat_service()     → CHAT_SERVICE 开关 → DeepseekService / OllamaService
├── create_reasoner_service() → REASON_SERVICE 开关 → DeepseekService / OllamaService
├── create_search_service()   → 固定使用 SearchService
└── （缺失）create_agent_service()  ← 未实现工厂方法

lg_builder.py（内联路由，不走工厂）
├── AGENT_SERVICE 判断 → 6个节点函数中重复内联
└── VISION_* 配置     → create_image_query 硬编码
```

### 2.2 根本原因

**视觉模型是后来追加的功能，没有纳入 `ServiceType` 枚举和 `LLMFactory` 路由体系。**

具体表现：
- `ServiceType` 枚举只有 `DEEPSEEK` 和 `OLLAMA`
- `LLMFactory` 没有 `create_vision_service()` 方法
- `create_image_query` 直接硬编码了 `VISION_*` 三个配置项，自行构造 HTTP 请求

这导致：**切换视觉模型需要同时改 VISION_API_KEY、VISION_BASE_URL、VISION_MODEL 三个配置项**，而不能像切换聊天服务那样改一个开关就行。

### 2.3 改进建议

如果要对齐设计，可以：

1. 在 `ServiceType` 枚举中增加视觉服务类型
2. 实现 `VisionService` 类（兼容 OpenAI 格式的 HTTP 调用）
3. 在 `LLMFactory` 中添加 `create_vision_service()` 方法
4. 在 `.env` 中增加 `VISION_SERVICE` 开关

**改进后效果**：
```bash
# 一行切换视觉模型服务商
VISION_SERVICE=deepseek    # 云端 DeepSeek
VISION_SERVICE=ollama      # 本地 Ollama
VISION_SERVICE=siliconflow # 硅基流动
```

## 3. 为什么要分 chat、reason、agent、embedding？

### 3.1 设计理念：按模型能力分层，而非按功能分类

不同任务对模型的能力要求差异巨大，用一个模型通吃所有任务会面临**三角困境**：

```
            效果好
            /   \
           /     \
          /   困境  \
         /         \
        /           \
     便宜 ───────── 快速
```

### 3.2 四种服务的定位

| 服务 | 核心要求 | 典型模型 | 如果混用的后果 |
|------|---------|---------|--------------|
| **chat** 聊天 | 对话流畅、响应快、成本低 | `deepseek-chat` / `qwen2.5:1.5b` | 用推理模型 → 太慢太贵；用 embedding 模型 → 不会聊天 |
| **reason** 推理 | 逻辑链长、多步推导、深度思考 | `deepseek-r1` / `deepseek-r1:7b` | 用轻量 chat 模型 → 推理容易出错、幻觉多 |
| **agent** 工具调用 | 函数调用、规划、遵循指令 | `deepseek-chat` / `qwen2.5:32b` | 普通 chat 模型 → 不会调工具，Agent 工作流直接崩溃 |
| **embedding** 向量化 | 文本→语义向量、相似度计算 | `bge-m3` / `text2vec` | chat 模型 → 生成不了语义向量，无法做检索 |

### 3.3 以当前配置为例的成本-效果分析

```bash
CHAT_SERVICE=deepseek          # deepseek-chat — 快、便宜、对话自然
REASON_SERVICE=deepseek        # deepseek-r1 — 推理能力强，专治复杂逻辑
AGENT_SERVICE=deepseek         # deepseek-chat — 支持 function calling
OLLAMA_EMBEDDING_MODEL=bge-m3  # 本地向量化 — 完全免费
```

| 服务 | 走哪里 | 成本 | 效果 |
|------|--------|------|------|
| 日常聊天 | 云端 DeepSeek | 低（轻量模型） | 对话体验好 |
| 复杂推理 | 云端 DeepSeek（r1） | 中（推理模型较贵） | 逻辑严密 |
| Agent 工作流 | 云端 DeepSeek | 中 | 支持工具调用和规划 |
| 文本向量化 | 本地 Ollama (bge-m3) | **免费** | 中文语义效果好 |

### 3.4 你的 5060Ti 可以如何优化

```bash
# 云端：推理和 Agent 走 DeepSeek（保证质量）
REASON_SERVICE=deepseek
AGENT_SERVICE=deepseek

# 本地：聊天和向量化走 Ollama（省钱）
CHAT_SERVICE=ollama
OLLAMA_CHAT_MODEL=qwen2.5:7b    # 7B 模型 5060Ti 绰绰有余
OLLAMA_EMBEDDING_MODEL=bge-m3   # 向量化本地跑，完全免费

# 视觉：想省也可本地
# ollama pull minicpm-v:8b
```

这样日常聊天几乎零成本，只有需要复杂推理和 Agent 编排时才走云端。

### 3.5 服务调用全景图

```
用户请求
├── 普通聊天 ──→ CHAT_SERVICE ──→ DeepseekChat / OllamaChat
├── 深度推理 ──→ REASON_SERVICE ─→ DeepseekReasoner / OllamaReasoner
├── Agent 工作流
│   ├── 查询路由分类 ──→ AGENT_SERVICE
│   ├── 通用回复     ──→ AGENT_SERVICE
│   ├── 追问引导     ──→ AGENT_SERVICE
│   ├── Cypher 查询   ──→ AGENT_SERVICE
│   ├── 研究计划     ──→ AGENT_SERVICE
│   ├── 幻觉检测     ──→ AGENT_SERVICE
│   └── 图片理解     ──→ VISION_*（独立配置，不走路由）
├── 文本向量化 ──→ EmbeddingService（硬编码 SentenceTransformer）
└── 联网搜索 ──→ SearchService（SerpAPI）
```
